## 1.35.0：视图快照（viewProbe）

- **新增 `[viewProbe]` 段和 `probeAfterMs`**：每次点击之后，对列出的类的实例各拍几张「此刻真实状态」快照，回答「那个控件在某一刻到底是什么状态」（点赞后玻璃图标不画，要看控件当时的真实状态，而不是靠猜）。
- **触发和时机**：触发源是屏幕上的一次点击（抬起且位置没动，和 `viewTap` 同一个钩子，不是每帧、不是轮询）。点击事件处理之前自动多拍一张「点击前」；之后按 `probeAfterMs`（默认 `0,200,1000,2500`）每个时间点用 `View.postDelayed` 排到界面线程各拍一张。任务外 / 暂停 / 浮窗关闭后不拍（和 `flowGate` 一致）。
- **每份快照每个控件一行**：类名@身份哈希、id、是否挂在窗口、`isShown`、可见性、位置和大小、`alpha`、`scaleX/Y`、`translationX/Y`、`isSelected`、前景（类名 + 边界 + 是否可见）、背景类名；ImageView 另记图片类名 + 边界、`imageAlpha`、drawable alpha；父级链前 3 层（类名、可见性、`alpha`、`clipChildren`）。
- **前后对比**：每张快照里同一个控件相对上一张变了什么，写成 `Δ imageAlpha 255→0`；新出现 / 消失的实例、「未找到实例：类名」也写出来。
- **找实例**：按类名遍历视图树（连父类一起匹配，最多 8000 个节点，每个类最多列 6 个实例）。
- **开销**：不写 `[viewProbe]` 不装钩子，没有任何额外开销。写了：每次点击 1 + 时间点个数 次一次性遍历，都在界面线程。每次点击一组，最多留 8 组。
- **输出**：导出里和视图树 / 点击同一节「视图快照 #n」，按时间排；时间线里有一条「视图快照 点击 (x,y)」标记。
- **检查器**：`viewProbe` 的类名写法 / 示例类名 / 没见过的类，`probeAfterMs` 的格式（全角逗号、带单位、空格分隔、超范围、重复、超过 8 个）；括号标记写错（如 `[viewProb]`）现在会提示最像的段名。新增文档同步检查：块格式的每个列表段名都必须写在手册里。
- 不能在电脑上验证的部分：钩子里读控件、`postDelayed` 排队、导出渲染只做了语法检查，要在真机上看。

## 1.34.0：让记录更干净（数据卫生 + 导出洁净度概况）

**数据卫生**
- 新增 `flowGate`（默认开）：任务浮窗「就绪」（窗口开了、还没点开始）和做过任务流程后「关闭之后」都按任务外处理，不记录。之前点开始之前、关浮窗之后目标 App 照旧全记，这些命中会混进同一条记录的总数，把导出里的频率分类（once / low / high）算偏，还会提前占满每种记录的上限。没用浮窗时不受影响。关浮窗后一直不记，直到「应用并重新记录」（或重新打开浮窗）。开了「任务外也记录」时这个开关不起作用。目标 App 在「就绪」期间重启也保持（补读最近的「浮窗就绪」标记）。
- 新增 `noiseQuota`（默认 50，%）：基线期间新建的记录最多占每种记录上限的这个比例。基线里周期性噪声很多，不限制会把上限占满，任务里新出现的位置就被丢掉（这也是「有记录却说没记录」的一个原因）。只限制「新建」，已有记录照常计数；被配额丢掉的条数在导出概况里按「种类.基线配额」写出。
- 任务结束 / 基线结束 / 浮窗关闭标记到达后，目标 App 立刻落盘（约 0.15 秒），不再等节流落盘。

**导出和浮窗的洁净度**
- 导出「任务清单的记录」开头新增「洁净度概况（按任务）」：每件事命中多少条 = 噪声（基线里也在周期性调用）+ 独有（只在这一件里出现）+ 共有（别的任务里也出现）；做多遍时每遍都出现的条数；含任务外命中的记录占多少；没录基线 / 命中全是噪声 / 没有记录会标 ⚠。导出开头的范围说明也改准确了：每条记录的总次数和频率是全程的，含任务外命中。
- 浮窗每件做完后显示同一组数字，代替原来的「有记录 / 没记录」。
- 检查流程修了会把有记录说成没记录的几处：先看记录条数（有记录就通过，不再因为时间线事件为 0 误判）；固定睡 5 秒改成约 1 秒后读，快照里还没有这件事的结束标记就隔 1.5 秒再读，最多 15 秒；记录上限满了会在原因里写明（以前一律说成「关键字 / 过滤挡掉了」）；原因里关于关键字的写法提示改成块格式。
- 统计算法在纯 Java 的 `TaskStats`，有单元测试；快照 JSON 的转换在 `TaskStatsJson`。

## 1.32.1：数据树可以展开控件的字段（treeViews）
- **问题**：数据树遇到控件（View）只记一行类名，`this` 是控件时整棵树都不展开。`X.0tdv#run` 这类计时任务里存着指回 `LongPressLayout` 的字段，但 `LongPressLayout` 里记了什么（按下位置 / 标志位）看不到，没法对比「没触摸」和「单击后」差在哪个字段。
- **改法**：新增配置 `treeViews`（默认关，设置页「数据树也展开控件的字段」）。打开后：①方法追踪的 `this` 是控件时也展开；②数据树里碰到业务自定义控件，展开它自己的字段（沿父类往上，到系统类为止）；③控件里碰到的别的控件仍只记一行，不往下走，免得顺着父子关系走遍整棵视图树。展开的节点照常受 `treeDepth` / `treeNodes` 限制，路径写法不变（`this.a.字段名`），值差异、观察点、`watch=` 都照常能用。
- **用法**：配置里加 `treeViews=true` `treeNodes=600`，方法追踪写 `X.0tdv#run`，任务清单做「对照」和要比较的操作，导出看「值差异」里 ✦ 的节点。
- 限制：没编译、没上机验证；只在方法命中的那一刻读字段，读的是当时的值；`treeNodes` 上限仍是 600，字段多的控件可能展开不完（导出会写「节点数到上限」）。

## 1.32.0：序列模式 @seq + 谁取消了待处理消息
- **按先后记的序列事件**：方法追踪行尾写 `@seq`（或 `@seq=N`），任务里这个方法每一次调用都在时间线记一条 SEQ（毫秒、线程、参数→返回值、耗时、栈顶 5 帧），不合并、不抽样。时间和序号取**进入方法时**的，外层方法排在它里面调用的方法前面。每个方法每个任务阶段默认 200 条（上限 1000），全部方法合计每阶段 1500、整个进程 6000；超出只计数，导出头部写明丢了多少（`timelineSeqDropped`）。单独存，不占 3000 条关键事件的额度。
- **采样计数按任务阶段重新数**：时间线采样（「前 5 次」）和 `want()` 的计数以前整个进程只数一次，高频位置在基线 / 上一个任务里就用光了，轮到要看的任务反而没样本。现在每次任务开始 / 重做 / 结束都从头数。
- **谁取消了待处理消息**：追踪 `android.os.MessageQueue#removeMessages` / `removeEqualMessages` / `removeCallbacksAndMessages`（Handler、WeakHandler 的取消最终都走这里）并写 `@seq` 时，进入方法时（返回后 Message 已被回收、字段清空）就在「已投递未执行」的消息里找出会被取消的那些，SEQ 行的 `⟦…⟧` 写出 what / callback / 还差多少毫秒执行 / 投递于多久前 / 投递线程和栈。需要 `chainOn` + `chainAsync`（没开会明确写出来）。
- **投递来源不再串号**：`Message` 对象会复用，限流没抓到来源时，旧版会让它带着上一次投递的旧来源；现在没抓到就清掉。
- 限制：投递来源每秒只抓前 300 条，取消的目标消息没被抓到时写「没有找到匹配的待处理消息」；没有上机验证，需要强杀目标 App 重开。

## 1.31.1：数据树不再只限方法追踪
- **实体树**：任务开始 / 结束 / 点「标记」时，把页面上扫到的数据实体（Aweme 这类，最多 6 类，各取一个实例）展开成数据树，树名「实体 类全名」，根叫 `entity`。两个时刻的值都记在当时的任务名下，对比能看出这一步改了哪些字段（受 `annotSweep` 和 `treeOn` 控制）。
- **视图所在树**：文字 / 图标记录创建时，顺着这个控件往上找它所在的 ViewHolder、第一个业务自定义控件、控件 tag，后台线程展开成树，树名「视图所在 类名」，根叫 `holder` / `view` / `tag`。不用写方法追踪也能看到「这段文字所在的对象里有哪些字段」。每种控件类前 3 次、之后每 50 次一次，全局至少隔 200ms。
- 这两类树没有观察点（没有能反复读取的根对象）；要追踪具体字段是谁改的，仍需把拿到该对象的方法写进方法追踪。
- 取不到的情况：对象不在页面可达范围内（静态单例、后台线程对象）时扫不到；文字所在控件既不在 RecyclerView 里、也不是业务自定义控件、tag 也不是业务对象时没有「视图所在」树。没在真机上验证过。

## 1.31.0：数据树 + 观察点 + 第二批标注（候选排名、值差异、时序、点击入口、结构指纹、钩子草稿、多遍命中率、可钩性）

- **数据树**（`treeOn` 默认开，`treeDepth` 4、`treeNodes` 200、`treeEvery` 10）：方法追踪命中时把 `this`、每个参数、返回值沿字段展开成树。每个节点有固定写法的路径：根 `this` / `argN` / `ret`，`.字段`、`[下标]`、`{键}`、`(LiveData)`、`(ref)`、`(lazy)`。每个路径记录它在每个任务里见过的值（每任务最多 4 个）。导出里「数据树」一节逐层画出来，值随任务变化的节点标 ✦，同一任务内就变过的标 ⇄。

2. 安装后在 LSPosed 启用，作用域勾目标 App（默认抖音 `com.ss.android.ugc.aweme`）。

## 采集原理
- `TextView.setText` 最底层汇聚方法 → 记**设置栈**，挂在该 TextView 上（只留最近一次）。
- `TextView.onDraw` 用 ThreadLocal 标记当前在画哪个 TextView；`Canvas.drawText/drawTextRun` 里取出它的设置栈，
  与**绘制栈**合成一条记录。没有 TextView 上下文的（自绘 / Compose）只有绘制栈，界面明确标注“无设置栈”。
- 归并 key = 设置栈签名 + 绘制栈签名 + View 类/id，**文字内容不进 key**，时长每秒变也只有一行，计数增长。
  每条记录会列出这个位置下**出现过的所有不同文字**（按文字形状去重，最多 40 种），所以整排标签合并成一行后仍能看到每个字，
  搜索也覆盖这些文字。
- **屏幕可见性**：采集阶段不过滤（预加载的内容也记，否则当前可见内容绑定时的设置栈会丢），
  写快照时才判断：每条记录弱引用最多 40 个 View（TextView 或图标），询问“已挂在窗口、可见、alpha 非 0、可见区域与窗口有交集”，
  通过的取它们**当前**的文字和屏幕坐标。列表里 ● 在屏幕上 / ○ 不在 / ? 未知（自绘、Compose 没有 View 可查，
  3 秒内画过算 ●，否则 ?，且不会被“只看屏幕上的”过滤掉）。该开关默认打开。
- TextView 的绘制栈只保留“这个 View 自己”的一段（到 View.draw 为止），祖先控件的 dispatchDraw 属于布局位置噪声，不参与签名。
- 限流：先用廉价“代理 key”（控件类 + id + 文字形状，数字折叠成 `#`，`00:12`≡`00:13`）判断是不是同一位置，
  同一位置只抓前 3 次栈，之后只计数；每 200 次抽样一次；全局每秒最多抓 1000 次栈兜底（冷启动一秒内文字很多，设太小会丢；被限流丢弃的次数会显示在列表顶部和导出文件里）。
- 栈清洗：去 Hook 框架帧、尾部系统帧；签名只看到最后一个 App 帧，lambda 编号等不稳定后缀被归一。
- 首次命中时后台线程反射查栈顶 3 个 App 帧的方法签名（`类#方法(参数类型):返回类型`，重载全部列出），
  再多带最多 3 个**没混淆**的帧（如 `androidx.compose.ui.text.MultiParagraph#paint-LG529CI`）。每行末尾标
  `[稳定]`（名字没被混淆，换版本大概率还能用）或 `[混淆·换版本会变]`；详情页和“只复制可hook签名”会先列稳定的，
  并给出一行“推荐 hook 点”。判断规则：类名 `X.xxx`、方法名 `LJxxx` / 单字母、类名只有 1~2 个字符 = 混淆。

## 1.3 新增
- **画笔 / 参数**：每次画文字都记画笔的颜色、字号、描边或填充（`Paint(color=0x.. size=.. style=STROKE|FILL)`），
  按变体去重（最多 16 种）。Compose 文字额外**自动观察** `MultiParagraph.paint*` 的参数，并和随后发生的 `drawText` 配对，
  记录里直接看到“这段文字 = 先描边 0x97000000、再填充 0xFFFFFFFF”。Compose Color 的打包 long 会自动标出 ARGB。
- **文字颜色设置位置**：hook `TextView.updateTextColors`（`setTextColor` / 样式 / XML 属性的汇聚点），记最近一次的颜色值和设置栈。
- **图标记录（kind=ICON）**：hook `ImageView.setImageDrawable/Resource/Bitmap/Icon/URI` 和 `View.setContentDescription`，
  记图标是谁设置的（资源名、Drawable 类名、位图尺寸、内容描述）。按钮上的图片不是文字，`drawText` 看不到，找“弹”这类按钮靠它。
- **方法追踪（kind=TRACE）**：配置里每行填 `类#方法`，只读地记录每次调用的**参数→返回值变体**和**调用栈（谁调用了它）**；
  不同调用位置各成一条记录。类还没加载时进入相关页面后自动重试，装不上的原因显示在列表顶部的 ⚠ 里。

- **自绘 / Compose 画布内坐标**（最近一次 drawText 的 x,y，不是屏幕坐标）。
- 文字截断从 60 字放宽到 200 字；每条记录跟踪的 View 从 16 个放宽到 40 个（评论列表等不再漏）。
- **导出文件头写明筛选条件**：“只看屏幕上”默认隐藏了多少条、编号是什么，免得看文件的人以为是漏记。
- 落盘：事件触发 + 单次延迟（默认 3 秒），写 `files/textrec/snapshot-<进程名>.json`；没有轮询、没有常驻定时器。
  配置热更新同样只在事件里顺带检查文件时间（≤2 秒一次）。

## 1.4 修正（根据 1.3 的真机导出）
- **推荐 hook 点不再乱推**：签名分四类——`[稳定]`（业务代码里没混淆的）、`[稳定·通用控件]`（`AppCompatImageView` / `DmtTextView` 这类，
  hook 后必须按 View 类/id 过滤）、`[稳定·通用基础设施]`（消息分发、LiveData、异步包装，永远不推荐）、`[混淆]`。
  每条签名带 `@栈第N层`（只数 App 帧），推荐只取离设置/绘制点 8 层以内的业务稳定帧；设置侧如果更近的只有混淆帧会加 ⚠ 提醒。
  设置侧、绘制/调用侧分别推荐；只有混淆名时再给一条**系统方法兜底**（`TextView#setText` / `View#setContentDescription` / `ImageView#setImageDrawable`，
  永远不会被混淆，但要按 View 类/id 过滤）。
- **图标资源名**：`AppCompatImageView.setImageResource` 是覆盖实现，不走 `ImageView.setImageResource`，1.3 里只看到
  `setImageDrawable drawable=BitmapDrawable 50x50`；现在单独 hook 它，记录里有 `res=资源名(0x资源id)`。
- 栈顶签名去重（构造方法链、重载链不再把同一个方法列两遍）。

## 1.6 精简与补充（根据 1.5 的真机导出）
17:58 那份 406 条的导出里 59% 的记录是“同一位置只是 View id 不同”的重复，14% 是 XML 布局加载栈，签名块重复拷贝占 23%。这版处理：
- **按位置合并**：归并 key 不再带 View id。同一段代码设置/绘制的一批控件合成一条，记录里列出全部 id（最多 60 个）。
  方法追踪的方法名、状态变化的方法名仍然进 key。

  标为“XML 布局里写死的设置”，不再解析、列出可 hook 签名（没有业务代码可 hook）。
- **栈尾裁剪**：尾部的 Handler / QmiHandler / bytex 异步包装这类通用基础设施帧从第一个这类帧开始截掉。
- **导出去重**：整份导出里，同一份调用栈、同一份签名块只完整写一次，后面的记录写“与 #N 完全相同，不重复列出”。
  记录详情页仍然显示完整内容。
- **状态变化记录（kind=STATE）**：hook `View.setAlpha / setVisibility / setSelected`，只记被跟踪的 View（画过/设置过文字，

  alpha 按 0.1 一档去重，动画不会刷出几十个变体。

## 1.26.3：任务清单新增第 4 段「空」，对照任务允许 0 条记录

- 背景：任务检查要求每件事期间至少有 1 条「记录」。方法追踪独占（`traceExclusive=true`）时，记录里只有 `traceMethods` 里的方法；「单击一次」这类对照操作调不到它们，一定是 0 条，被误判为未通过。
- 写法：清单每行 `名称|提示|秒数|空`。第 4 段写 `空`（也可写 `0`、`可空`、`对照`）= 对照任务。例：`单击一次|在视频中间只单击一次，停 3 秒||空`（秒数留空，所以是两个竖线）。
- 行为：带 `空` 的任务 0 条记录算通过，提示「对照任务：这件事期间 0 条记录（符合预期）」；但这件事期间仍要有操作事件（点击、按键），一个都没有照样报错。没写 `空` 的任务检查不变。
- 升级后要先点浮窗「✕」关掉，再重新打开，浮窗才会读新清单。

## 1.26.2：修正配置页的数字框空白、开关全关、保存后退回默认值

- 原因：发布版开了代码混淆（R8），配置页按字段名反射读写 `RecConfig`，字段被改名后全部找不到，异常又被吞掉。表现是「更多细分项」里的数字框空白、子开关全关，「回填并保存」时空框一律退回默认值，粘贴的 `capTrace`、`traceDumpLines`、`traceDumpDepth` 都不生效。
- 修正：`proguard-rules.pro` 里保留 `RecConfig` 的公开成员原名。
- 升级后请重新粘贴一次配置再保存、推送：旧版已经存下来的配置里，这些项是被重置过的默认值。

## 1.26.1：导出里写出目标进程实际生效的字段快照配置

- 导出文件开头新增一行「字段快照（目标进程实际生效）」，写 `traceDump` `traceDumpEvery` `traceDumpLines` `traceDumpDepth` 在目标 App 进程里的当前值。快照长度不对时，先看这一行就知道是配置没推送到，还是目标进程里跑的是旧版模块。
- 「方法追踪字段快照」补上 `traceDumpEvery` 的输入框。以前它没有输入框，「回填并保存」会把配置里写的值重置成 25。

## 1.26.0：字段快照的行数和层数可调

- 方法追踪的「记录对象字段值」原来写死只取 40 行、最多展开 3 层，字段多的对象（如抖音的 `Aweme`）列不到后面的字段。现在做成两个配置项：
  - `traceDumpLines`：一份快照最多多少行，默认 40（和以前一样），范围 10~2000。
  - `traceDumpDepth`：往子对象里最多展开几层，默认 3（和以前一样），范围 0~6；0 = 只列对象自己的数值 / 布尔 / 文字字段，不进子对象。
- 「高级 → 更多细分项」新增「方法追踪字段快照」两个数字框，「回填并保存」会读写它们。
- Compose 字段展开（`composeDumpLines`）不受影响，仍按原来的 3 层。
- 用完请调回默认值：快照变大后导出文件也会变大。

## 1.25.0：任务内 / 任务外分两桶，只记任务清单

用任务浮窗录的时候，原来任务之间的操作（翻界面、等页面出来）也会进记录，记录里夹着大量和任务无关的东西。这版：

- **任务检查改严**：浮窗判断一件事「记到了」，现在必须这件事期间真有记录（用每条记录的 segCounts 数），不再只数点击 / 页面切换这类时间线事件；有操作但一条记录都没有会停下来写原因。
- **首页顶部「复制 AI 说明」按钮**：把 assets/ai_guide.md（与根目录《AI使用说明.md》相同，改一处要同步改另一处）整份复制到剪贴板。
- **首页顶部「粘贴配置和任务清单」**：一个常驻输入框（在「目标 App」上面），采集配置（`key=value`）和任务清单（`名称|提示|秒数`）混着粘贴，程序按行自动区分（规则见 `RecConfig.splitPaste`；任务名像 `key=` 时可先写一行 `[任务清单]`）。「回填并保存」= 配置回填表单（不推送）+ 任务清单存起来；「打开浮窗」= 先同样保存再打开浮窗。**AI 生成配置时必须同时给出任务清单。**
- **任务浮窗显示下一件**：「正在做」面板绿色调，「下一件」面板灰蓝调，带名称和提示，方便提前准备；暂停 / 完成 / 准备阶段各有自己的颜色标签。
- **方法追踪独占（`traceExclusive`，默认开）**：「方法追踪」里填了方法时，目标 App 里自动把文字 / 图标 / 颜色 / 状态 / 绘制 / Compose 观察这些记录开关当成关闭，记录里只剩方法追踪；只改运行时副本，界面开关和配置文件不动，清空方法清单后自动恢复。关掉它可以让方法追踪和其他记录一起记。实现见 `RecConfig.applyTraceExclusive()`。
- **方法追踪能追任何方法**：框架 / 系统类（`android.*`）也能找到；写的类自己没声明该方法时，会自动挂到父类或接口 default 方法的声明处，用 `this` 过滤，记录仍按你写的「子类#方法」归档。`类#*` 只含类自己声明的方法。
- **方法追踪和浮窗任务**：方法追踪和其他记录走同一套任务内 / 任务外逻辑（`Timeline.skip()` / 分桶），可以连续做多个任务。
- **默认只记任务内**：任务浮窗的流程开始后，只有「任务开始 → 任务结束」之间才建记录、记时间线样本。任务之间、「暂停记录」期间是**轻模式**：不建记录、不记样本、不进时间线，但 `setText` 仍然维护“控件 ← 设置栈”的对应（否则任务里画出来的文字查不到是谁设置的），方法追踪的标识（视频 id）也照常更新；标记、页面切换、基线照常记。基线算任务内。
- **开关「任务外也记录」**（首页，时间线上方，默认关）：打开后任务外也记，但**单独一桶**：同一个位置在任务内、任务外各有一条记录，各自计数；每种记录的上限分开算（`TRACE` 和 `TRACE(任务外)` 各 600），任务外灌满不会挤掉任务内；分文件存时任务外的文件名带 `.OUT`（`snapshot-<进程>.<种类>.OUT.json`）。
- **不用任务浮窗时不受影响**，照旧全记（全部算任务内）。浮窗关闭（含「✕」）后目标进程退出“任务流程”状态，也恢复全记。「任务全部完成」之后到关浮窗之前仍按任务外处理，收尾操作不会混进任务内。
- **记录页顶部新增「范围」芯片**：点一下在 任务内 → 任务外 → 全部 之间切换，默认任务内。
- **导出新增「任务清单的记录（txt）」**：只导出任务内桶里、在任务清单上任意一件事期间被调用过的记录；不看当前的类型 / 页面 / 仅屏幕上 / 隐藏公共控件筛选。文件头列出任务清单全部任务，并写明哪几件事期间一条记录都没有；每条记录里的「按任务阶段的调用次数」说明它在哪几件事里出现了几次。想只看某一件事，导出后搜 `任务3`。
- 已知局限：任务开始标记经 root 写文件、目标进程再读，有零点几秒延迟，点开始后最前面的动作可能漏，建议点开始后等一秒再操作；任务结束标记同理，结束后的最后一点动作可能还算在这件事里。浮窗所在的 TextRec 进程被杀、没发出“浮窗关闭”时，目标进程会一直停在任务流程状态（只记任务内），强杀目标 App 重启后恢复。**未在真机上验证过，也没有完整编译（环境里没有 Android SDK），只做了语法和符号检查。**

## 1.22.4：先开始的任务、没记录到时写出原因、按任务阶段计数

- **先启动还是后启动**：任务清单没写 `!` 时，一律是「先启动目标 App、切到它的界面，再在浮窗点开始」。第一件的名称前写 `!`（如 `!冷启动抖音|强杀后点图标启动，等首页出来，再点 ▶ 下一件`），浮窗一打开就直接开始这件事，用于要在目标 App 还没运行时就开始的任务。规则也写在「编辑任务清单」窗口里。
- **冷启动前发出的标记补读**：目标进程启动时，从标记文件里补读最近一条「任务流程开始」之后（5 分钟内）发出的标记，时间会是负数，意思是进程启动前发出的。冷启动时钩子还没装上，进程启动前几百毫秒的调用记不到，只能记“用户在做冷启动”。
- **没记录到就写原因**：点 ▶ 下一件时，浮窗先发结束标记，等约 5 秒让目标进程落盘，再经 root 读回快照检查这件事期间有没有记录到事件。没有就停在这件事上，用黄色字写原因（读不到快照 / 目标进程没收到开始标记 / 这件事期间一个事件都没记到），并列出各进程收到标记的情况、采集配置、统计和警告；点「复制原因」整段复制，发给 Claude。还有「重做」「忽略继续」「关闭」。基线这件事不要求有事件，只检查标记到没到。每次点下一件因此要多等约 6 秒。
- **按任务阶段计数**：每条记录多一行「按任务阶段的调用次数」，如 `任务2 12  任务3 0  任务4 31`，能看出某个位置在暂停那几秒还在不在被调用。没出现的任务 = 0 次。

## 1.22.3：浮窗先停在“准备”，切到目标 App 再按开始

浮窗打开后不再直接开始第一件事，而是停在「准备」：标题写“先切到「抖音」界面”（目标 App 的应用名），只有 ✕ 关闭 和 ▶ 开始 两个键。切到目标 App、让视频已经在播之后再点 ▶ 开始，第一件事（比如基线倒计时）才开始，并发出“任务流程开始”标记。以前先开浮窗就开始倒计时，倒计时走完目标 App 才启动，基线就是空的。

## 1.22.2：被挤掉的事件分开存、相同的合并

之前所有采样事件（控件加入视图树、图标、清空、状态……）共用每种 400 条的额度，先到的灌满后，后面的任务阶段就没有了（上一份导出里控件加入视图树被丢了 7710 条）。现在：
- 完全相同的事件（同种类、同任务阶段、同内容）合并成一条「×N（最后一次 +时刻）」，重复出现不占额度，信息不丢。
- 不同的事件按「种类 × 任务阶段」分开，各记前 150 种不同的；某个任务阶段灌满了，不会影响别的阶段。
- 超出额度的只计种数，导出时间线头部按“种类(任务N)”写明各丢了多少种。
- 任务阶段由浮窗的「任务开始 N / 重做 N」标记决定，没用浮窗时都算“任务之外”一个阶段。

## 1.22.1：标记丢失修正（根据 1.22.0 的真机导出）

真机导出里，目标 App 主进程只收到了第一条标记（基线开始，还晚了 6.5 秒），之后的任务开始 / 结束、基线结束全丢了；另一个沙盒进程反而收齐了。原因推测是：标记写成同一个文件反复覆盖，目标进程读得慢就漏掉中间几条；文件监听线程又可能被目标 App 自己的监听堵住（没法在没有真机日志的情况下证实，所以两处都改）。

- 标记改成追加写 `markers.log`，一行「序号|发送时刻|内容」；目标进程记住读到哪里，每次把新增的行全读走。
- 目标进程另起一个小线程，每 200ms 看一次文件长度，不再单靠文件监听。
- 基线带时长（浮窗发「基线开始 10」），时间一到自动结束；结束标记丢了也不会把后面所有记录都算成基线（上一版就是这样，所以记录里没有“基线”一行）。
- 没开始就收到「基线结束」时不再记出一个几十亿毫秒的时长。

## 1.22.0：任务浮窗 + 时间线修正

**任务浮窗**（记录页右上「更多」→「任务浮窗」，首次要给 TextRec 开「显示在其他应用上层」）：浮在所有 App 上面，一步一步提示现在要做什么（默认清单：基线 10 秒、划到下一个视频、暂停、继续播放、拖进度条回退、进评论再返回，可在「编辑任务清单」里改，一行一件：`名称|提示|秒数`，名称写 `@基线` 是自动计时的基线）。四个键：✕ 关闭、↺ 重做（这一件重来，上一次作废）、◀ 上一件、▶ 下一件。每件事开始、结束、重做、中止都作为标记经 root 推给目标 App 的时间线；每件事开始短震一下；按住浮窗上方的文字可以拖动。浮窗在 TextRec 自己的进程里，不往目标 App 里画东西。导出时间线里被「重做」作废的那一次，每行前面标 ✗。标记按 TextRec 发出的时刻推算时间，不按目标进程收到的时刻。

**时间线修正**（根据 1.21.0 的真机导出）：
- 标记 / 基线 / 任务 / 点击 / 返回 / 页面 / 标识 / 钩点可用这些关键事件单独存，不会再被高频事件挤掉（上一版标记被挤丢了）。

- 点击事件多带控件的文字、描述和三层上级，不再只有 FrameLayout。
- 同一百毫秒内连续的页面切换（碎片恢复顺序）合成一条。

## 1.21.0：时间线、标记、基线、用途分类（对应“改色 / 隐藏 / 换文字 / 跳过”四种用途）

**时间线**（首页「时间线」，默认开，有三个开关）：把用户操作（点击 / 滑动 / 长按 / 返回键，带坐标和点中的控件）、页面切换、钩点第一次可用、各位置的记录样本（方法追踪、setText / 清空 / 图标 / 状态变化 / 控件加入移出视图树；每个位置前 5 次，之后每 100 次一条）按单调时钟毫秒 + 序号排成一条，导出 txt 开头有「时间线」一段，json 里是 `timelineText`；上限 3000 条，丢了多少会写出来。

**标记 / 基线**（记录页右上「更多」）：「打标记」在时间线上记一笔“现在开始做某某”；「基线：开始 / 结束」录一段什么都不操作的时间，期间被调用的位置在记录里标“基线里也在调用”（周期性噪声）。标记经 root 写进目标 App 的 `marker.txt`，目标进程监听文件读到。

**每条记录新增**：用途 / 触发原因（用户操作、帧回调、数据变化、消息、同步，按栈判断）；首次 / 最近时间、相邻两次间隔最短最长、约每秒次数；基线分账；出现时的当前标识（方法追踪行写 `@tag=0`，取第 0 个参数当标识，如视频 id；`@tag=ret` 取返回值）；this 的对象身份值（同一对象还是每次新建）；钩点信息（同名重载及签名、final / 静态 / 抽象 / 合成、类名方法名是否疑似混淆、类加载器、第几次尝试时可用）；栈上各层出现次数（每份采样栈都出现的层 = 稳定层）；方法追踪的栈放宽到 30 层。环境（机型 / 系统 / ABI / App 版本）写在导出头部。

**分类新增 4 个维度**：用途（color 改色 / hide 隐藏显示 / text 换文字 / skip 跳过·通用方法 / other）、基线（noise / live / unknown）、触发原因（touch / frame / data / msg / sync / none）、视频/标识。命令：`purpose=` `baseline=` `trigger=` `tag=`；`full=3,5,9` 让导出只给这几条完整细节，其余一行摘要。用途可以同时有几个，筛选按“包含”；它是按记录类型、方法名、返回类型给的提示，不是保证。

**控件加入 / 移出视图树**：钩 ViewGroup.addView / removeView，进时间线，用来看延迟创建和回收复用。

已知局限：基线 / 标记依赖 root 推送；栈层统计是采样栈里的出现次数，不是真实调用次数；“跳过之后紧跟着调用什么”要开 1.20.0 的链路追踪看下游；Compose 没有 View，只能看栈里的节点层级；协程 / RxJava 的异步来源不覆盖；未在真机上验证过。

## 1.20.0：链路追踪（默认关，有总开关和三个子开关）

以「方法追踪」里的任意一个方法为落脚点，记下它的上游和下游，显示在那条记录的详情和导出里（「链路追踪」一段）。

- 上游：同步调用栈本来就有；新增「异步来源」——钩 Handler 消息队列和线程池，记下现在跑的这段代码是谁、在哪个线程投递的，投递者自己又是被谁投递的，最多追 6 层。
- 下游·被调用的方法：锚点所在的类、以及它 this 里同包字段所属的类（最多 8 个类、300 个方法）被临时钩住，只在锚点执行期间记先后和嵌套。
- 下游·界面效果：锚点执行期间发生的 setText / 清空 / 图标 / 状态变化；锚点期间投递的异步任务稍后跑起来时做的事，也接在同一条链后面（3 秒内）。
- 采样：前 5 次每次建链，之后每 20 次一次；链里最多列 120 个被调用的方法。
- 已知局限：没有改 ART 的方法追踪；只有“锚点执行期间 + 它投递的任务”里发生的事才算下游，之后别处（例如下一帧 vsync）发生的绘制不会算进来；同步方法里调用了锚点所在类和同包字段类以外的类，只会在效果里看到结果，看不到中间调用；非链路内的异步投递每秒最多抓 300 次来源。未在真机上验证过。

## 1.19.3：setText 空串 / null 也记（清空文字）
- 以前 `setText("")` / `setText(null)` 直接丢掉，还会清掉这个控件之前的设置栈配对，所以"谁把这段文字清空了"完全看不到。现在单独记一类 `TEXTCLEAR`（记录页标签「清空文字」），归在「文字（TextView）」类型下。
- 记录内容：View 类 / id、**谁清空的（设置栈，和 setText 一样抓栈、同样受限流）**、清空次数；文字栏显示 `（空串）`，搜「空串」能搜到。按 (View 类, 设置栈) 归并，同一位置清空 N 次只有一条。
- 空串没有绘制，所以不受「仅屏幕上」影响（和「没显示的文字」一样）。
- 受「文字是谁设置的」开关控制；「只记关键字」模式下不记（空串不会命中关键字）。
- 只覆盖 `TextView.setText`；`append("")`、`setHint("")` 不算清空，仍不记。
- 没有在真机上验证过；这版也只做过语法检查。

## 1.19：方法追踪记「对象字段值」
找进度条、时长这类**状态**存在哪里时用（比如进度值每帧发给谁、总时长放在哪个字段）：
- 「高级 → 方法追踪」下方新增开关「记录对象字段值」（配置字段 `traceDump`，`traceDumpEvery` 默认 25）。
- 快照按 `类#方法` 统计：同一个方法因为调用栈不同会有好几条记录（拖动那条、播放那条……），它们共用同一份快照，哪条都能看到。
- 打开后，方法追踪的记录详情「概览」页多一段「状态快照」：从被追踪的对象（`this`，比如观察者）出发，沿字段往下最多 4 层，列出数值 / 布尔 / 文字字段，LiveData 里当前的值也会读出来（`(LiveData) = …`）；最多 40 行，只留最近一份。
- 同一段还给出第一个数值参数的 `last / min / max`。把进度条拖到最右端、再拖到最左端，max / min 就是满量程，用来判断单位。
- 状态快照在「压低高频方法」之前处理，所以降频之后仍然每隔 N 次更新一份；关着开关时没有任何额外开销。
- 读 LiveData 的值时已处于 BUSY 状态，不会因此又触发被追踪的方法。快照文字也能被搜索、被「复制全部」带出。
- 没有在真机上验证过；这版也只做过语法检查。

## 1.18：采集过滤（挡掉不相关的，抓栈之前就判断）
首页新增「采集过滤」卡片，**全是开关和分段选择，不用填空**。**全部关掉 = 和 1.17 完全一样（默认不过滤）**。被挡掉的调用不抓栈、不建记录，只累加“挡掉了多少次”，显示在记录页顶部的概况行里（`已挡掉：触发窗口 N / 线程 N / …`），记录不够时先看是不是被哪个开关挡掉了，把它关掉。

| 开关 | 作用范围 | 说明 |
|---|---|---|
| 触发窗口：不限 / 1.5 秒 / 3 秒 / 5 秒 | 方法追踪；打开「也用于文字 / 图标 / 状态」后全部 | 最近一次触摸后这段时间内才记。靠 hook `Activity.dispatchTouchEvent` 写一个时间戳（只在选了窗口时才装）；Dialog / PopupWindow 里的触摸和不调用 super 的 Activity 看不到 |
| 排除通用基础设施 | 方法追踪 | 不记 LiveData、Fragment 生命周期、字节异步包装等几乎所有功能都会经过的类 |
| 线程：全部 / 只主线程 / 只后台线程 | 全部 | 用 Looper 判断主线程，不看线程名 |
| 只记带时间的调用 | 方法追踪 | 参数或返回值摘要里有 `00:00` 形式的文字才记，找视频时长用 |
| 压低高频方法 | 方法追踪 | 同一位置超过 50 次且持续超过 3 秒后只计数、不抓栈 |

需要手写内容的条件（线程名、页面、控件、额外排除、额外值匹配）放在「高级 → 手写过滤条件（可选）」，留空不起作用。手写值匹配时长会自动展开：`01:37` → `01:37`、`1:37`、`97`、`97000`；短于 3 位的纯数字不加入。摘要里字符串只留前 60~80 字符，藏在大对象里的值匹配不到。排除名单每行：`类#方法`、`类#*`、`#方法`、类名 / 包名前缀。

### 方法追踪的新写法
- `类#*`：追踪这个类自己声明的所有方法和构造方法（跳过抽象 / native / 合成方法）。调用很多，配合排除名单和触发窗口用。
- 行尾选项（空格分隔）：`@count` 只计数；`@args` 只记参数 / 返回值变体、不抓栈；`@stack=4` 这一行单独的栈深度；`@every=10` 这一行单独的抽样间隔。例：`X.1Abc#LIZ @count`。
- 带 `@count` / `@args` 的记录没有调用栈，是预期行为。

### 预设
- 「找钩子（最窄）」：只设置采集过滤：触发窗口 1.5 秒 + 排除通用基础设施 + 压低高频方法。不动「记录哪些内容」的任何开关。
- 「关掉全部过滤」：全部恢复不过滤。

### 没有在真机上验证过的地方
- 这版只做过语法检查（没有 Android SDK 编译），请先构建、跑一遍再用。
- 改过滤开关靠配置热更新（inotify），按现有代码应该不用强杀重开；新增追踪方法在类还没加载时会自动重试。

- 记录列表新增“页面：…”按钮，选中后列表和导出（txt / JSON）都只含该页面；导出头部会写明页面。
- 记录按“记录那一刻所处的页面”归属：切页面时预加载的内容会算在当时的页面下，标记为 ○ 不在屏幕上。

## 1.7：清空记录后，屏幕上已经显示的内容也能被记录
- **原因**：记录是事件驱动的（setText / drawText / setImage*）。硬件加速下，静态不变的文字不会再被绘制，所以点“清空记录”之后，
  底部的首页/朋友/消息/我、顶部的同城/游戏等标签没有任何事件，一直是空的，点一下（触发重绘）才冒出来。
  另外旧版读到“清空”还要等下一次 hook 事件，并且会把“View → 设置栈”的对应一起清掉，重绘后的记录也没有设置栈。
- **配置监听**：目标进程用 inotify（`FileObserver`）监听 `config.properties`，模块一改配置（含“清空记录”）立刻生效，不轮询，不用等事件。
- **清空后重新采集**：在界面线程遍历当前窗口——可见的文字控件 `invalidate()` 重画一次（走正常的 drawText 记录）；
  图标 / 带内容描述的控件直接补一条“屏幕扫描”记录。只读，不改内容。
- **清空只清记录**：不再清掉“View → 设置栈 / 文字颜色栈”的对应，重画后的记录仍然带设置栈。
- 图标记录里带“屏幕扫描”且没有设置栈的，说明设置发生在模块启动之前（冷启动、没被抓到）。

## 命令（记录页 → 顶栏「更多」→「粘贴命令…」）
一行文本 = 一套筛选条件。任何人/任何 AI 只要照着下面这张表拼一行、让用户粘贴进那个输入框、点「执行」，
不需要知道代码怎么写、不需要来问开发者。执行时**先清空当前所有筛选，再按这行命令重新设置**，
所以同一行命令什么时候粘贴、粘贴几次，结果都一样。

格式：空格分隔多个 `key=value`；不带 `=` 的词当搜索词（和搜索框一样，多个词要同时命中文字才算中）。
无法识别的 key，或 value 在当前数据里根本不存在，会被忽略并在执行后用一行 toast 报出来，不会让整条命令失败。

`container=` `module=` `view=` `page=` 四个是开放词表（取决于目标 App 实际有什么类名/包名/页面），
**大小写不敏感、子串匹配**：比如抓到的容器叫 `CommentItemView`，写 `container=comment` 也能命中；
如果子串能匹配到好几种，取第一个命中的，想精确一点就把词写得更完整。

下面这些是封闭词表，必须完全照抄（小写，不认中文，不认全角括号）：

| key | 取值 | 对应的是 |
|---|---|---|
| `kind=` | `TEXTVIEW` `CANVAS` `COMPOSE` `ICON` `TRACE` `TEXTSET` `STATE` `all` | 记录类型（和导出 JSON 里 `kind` 字段原始值完全一致，大小写不敏感；`all`=不限） |

## 已知限制
- Compose 没有 `setText`：只有绘制栈，“谁算出这段文字”要靠盯参数找。
- 代理 key 相同（同类、同 id、同形状）但来自不同代码路径的，前 3 次之后靠每 200 次抽样才能发现。
- 直接改 `Editable` 的文本变化（输入框里敲字）不会被记录。
- 图标只覆盖 ImageView 和有 contentDescription 的 View；纯 Canvas 画的位图/矢量（`drawBitmap`、Compose `Image`）暂不记录。
- Compose 的自动参数观察只针对 `MultiParagraph.paint*`；其他 Compose 内部方法用“方法追踪”手动加。
- 全量模式会拖慢目标 App，只在调试时开。
- 抖音更新后混淆名会变，每条快照带 App 版本号。
- 方法追踪若追踪每秒调用上千次的方法会拖慢目标 App（超过 3000 次后自动降为每 10 次取样一次）。
- 本模块只记录，不修改颜色或隐藏；那些交给单独的改色/隐藏模块。


## 1.5：记录“只设置、从未绘制”的文字
- 背景：TextRec 之前只在**绘制**时建记录。控件为 INVISIBLE / GONE / 尺寸为 0 / 未挂窗口 / 祖先不可见时，
  系统不会调用它的 `onDraw`，即使 App 每秒都在 `setText`（例如拖动进度条才显示的时长），也不会留下任何记录。
- 现在 `setText` 时就登记“这个位置设置过文字”（类型 **仅设置**，按 View 类 + id + 设置栈归并，每个位置一条）。
- 是否“从未绘制”在**写快照时**才判断：该位置跟踪的 TextView 里，`TextView.onDraw` 从没执行过的才算。
  控件后来被画了，这条记录就自动消失（已有对应的 TextView 记录），不会和它重复。
- 记录里给出这些控件**当前**的文字（时长会实时变）和**没被画的原因**：自身 GONE / INVISIBLE、
  祖先 xx 为 GONE、未挂到窗口、尺寸为 0、alpha≈0，或“可见且已布局但还没画”。
- 这类记录单独限额（默认 500，配置页可调），满额只计丢弃数，不影响其他记录；概况行会提示。
- 它们默认被“只看屏幕上的文字”隐藏（本来就不在屏幕上）。在列表里把类型切到“仅设置”就能直接看到，
  此时不再套“只看屏幕上”。用法：搜 `re:\d{1,2}:\d{2}` 找时长。
- 已知限制：子类如果重写 `onDraw` 却不调用 `super.onDraw`，TextRec 看不到它的绘制，会把它当成“从未绘制”，
  此时原因一栏会显示“可见且已布局，但还没被绘制……”。
